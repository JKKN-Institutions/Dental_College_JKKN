Issue 1 — Rewrite Titles for Click-Through (CTR)

P1 Pages rank on Google but nobody clicks

What's wrong

In Search Console these pages show impressions (e.g. "dental college in erode" sits at position 6.3), but 0 clicks in 28 days. The page title shown in Google results is not compelling enough — aggregator sites (Collegedunia, Shiksha) win the click. We add a proof + offer hook (placement %, BDS 2026, distance) while keeping the exact ranking keyword at the start of the title. All titles stay under 60 characters.

Where

Each page's metadata lives in its layout.tsx file, not page.tsx. The title appears in 3 places per file — update all three so the SERP, Open Graph (social), and Twitter card stay consistent:

  • metadata.title.absolute — the main SEO title

Issue 2 — Fix Namakkal Mobile Performance

P1 Namakkal is the slow outlier

What's wrong

Mobile Lighthouse: performance 65/100, Total Blocking Time 1,230ms, LCP 3.1s. The other 4 pages (built from the same template) have TBT of just 130–510ms. So something on the Namakkal page specifically is blocking the main thread 5–9× longer. This hurts mobile rankings and bounce rate.

Where

app/namakkal/page.tsx (and its layout.tsx)

How to find & fix (investigation, not a blind edit)

  • Reproduce: npm run build && npm start, then run Chrome DevTools → Lighthouse (mobile) on /namakkal/. Open the Performance tab → record a load → look at the longest "Long Tasks" on the main thread.
  • Diff against the fast page: compare app/namakkal/page.tsx with app/tiruppur/page.tsx (TBT 130ms, the fastest). Namakkal has extra sections and a longer content body — find what Tiruppur does NOT have.
  • Look for these usual suspects: a heavy "use client" component rendered above the fold a non-lazy carousel / map / video embed a very large inline array rendered on mount framer-motion animating many elements at once
  • Fix pattern — lazy-load below-the-fold heavy widgets:
import dynamic from 'next/dynamic';

// load only when needed, skip during SSR for non-critical widgets
const HeavyWidget = dynamic(() => import('@/components/HeavyWidget'), {
  ssr: false,
  loading: () => null,
});
  • Add loading="lazy" to every below-the-fold <img> on the page.
  • If framer-motion is animating long lists, gate animations with whileInView + viewport={{ once: true }} instead of animating everything on load.
Target / How to verify: Re-run mobile Lighthouse on /namakkal/. Goal: TBT < 300ms, performance > 85 (matching its sister pages). Also confirm the page still renders identically across breakpoints (375px, 768px, 1024px).

Issue 4 — Add Rich-Result Robots Directives (Salem & Tiruppur)

P2 Salem & Tiruppur use a bare robots block

What's wrong

Erode and Coimbatore allow large image previews and full snippets in Google (max-image-preview: large etc.), which makes results visually richer. Salem and Tiruppur only have { index: true, follow: true } — missing those rich-result hints.

Where

app/salem/layout.tsx (line 10)  and  app/tiruppur/layout.tsx (line 10)

BEFORE

robots: { index: true, follow: true },

AFTER

robots: {
  index: true,
  follow: true,
  'max-snippet': -1,
  'max-image-preview': 'large',
  'max-video-preview': -1,
},
How to verify: npm run build, then view page source → the <meta name="robots"> tag should now include max-image-preview:large.

Issue 5 — Preload the Hero (LCP) Image

P3 Push LCP under 2.5s

What's wrong

Largest Contentful Paint is above the 2.5s target on Namakkal (3.1s), Coimbatore (3.0s) and Tiruppur (2.7s). The hero image /images/BDS-hero-image.webp is the LCP element. Preloading it helps the browser fetch it sooner.

Where & how

Best approach in Next.js: if the hero is rendered with next/image, add the priority prop to it (this auto-generates a preload). Find the hero <Image> in each app/[city]/page.tsx:

<Image src="/images/BDS-hero-image.webp" alt="..." priority />

If the hero is a plain CSS background or <img>, add a preload link in the layout instead:

// inside the layout return, before <Header />
<link rel="preload" as="image" href="/images/BDS-hero-image.webp" />
How to verify: Mobile Lighthouse → LCP should drop below 2.5s. Confirm only ONE preload per page (don't double up).

Issue 6 — (Optional) X-XSS-Protection Header

P3 Low value — read before doing

What the audit flagged

An automated scanner reported the X-XSS-Protection header is missing on all 5 pages.

Honest recommendation: This header is deprecated. Modern browsers ignore it, and in some old browsers it could even introduce issues — current security guidance (OWASP) is to either omit it or set it to 0. The site already has a strong Content-Security-Policy, which is the real XSS defense. You can safely skip this. Only add it if a compliance checklist explicitly requires the header to be present.

If you must add it

next.config.ts → inside the headers() array for /(.*):

{ key: 'X-XSS-Protection', value: '0' },
